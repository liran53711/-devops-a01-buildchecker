## E5：原始复现

### 步骤与命令

```bash
cd labs/A-buildchecker
python3 scripts/lab_cloud.py e5 --out work/e5-02
```

该命令在容器内执行：

```bash
cp -R /app/fixtures/md-rd/. /evidence/
cd /evidence && mkdir trace
make clean
strace -ff -s 4096 -o trace/t -e trace=%file,%process make -p app > make-db.txt 2> build-stderr.log
./app > program-output.txt
```

### 原始输入

`fixtures/md-rd/`：

```makefile
app: main.o
	$(CC) main.o -o app

main.o: main.c unused.h
	$(CC) -c main.c -o main.o
```

```c
/* main.c */
#include <stdio.h>
#include "config.h"
int main(void) { printf("%d\n", MODE); return 0; }
```

### 预期与实际输出

| 检查项 | 预期 | 实际 | 退出码 | 证据路径 |
|---|---|---|---|---|
| 程序输出 | `1` | `1` | 0 | `work/e5-02/evidence/program-output.txt` |
| Makefile 声明 | `main.o: main.c unused.h` | 同左（`make-db.txt` 第 1061 行） | — | `work/e5-02/evidence/make-db.txt` |
| 实际读取 `config.h` | trace 中存在成功打开记录 | `t.16:580` | — | `work/e5-02/evidence/trace/t.16` |
| 缺失依赖 MD | `main.o → config.h` | 一致 | — | 见 E6 |
| 冗余依赖 RD | `main.o → unused.h` | 一致 | — | 见 E6 |

**关键 trace 行**（`work/e5-02/evidence/trace/t.16` 第 580 行）：

```text
openat(AT_FDCWD, "config.h", O_RDONLY|O_NOCTTY) = 4
```

说明：本次运行 `cc1` 进程 PID 为 16，与课件示例中的 `t.33` 不同；PID 每次运行都会变化，不影响结论。

### 与论文原型的差异

| 论文 | 本实验 | 影响 |
|---|---|---|
| 直接使用 ptrace | 使用 `strace -ff -s 4096 -e trace=%file,%process` | 记录粒度相同，但依赖 strace 的输出格式 |
| 30 个 GNU Make / CMake 开源项目 | 1 个最小 GNU Make 样例 | 只验证流程正确性，不验证泛化能力 |
| 通用依赖推断 | 仅把**成功的 `O_RDONLY` open** 记为实际读取 | 不能证明字节真的被读，只能证明打开成功 |
| 完整进程模型 | 只支持单个 Make 进程树、每个 recipe 一个最终输出 | 递归 Make、多输出任务会显式报 `UNSUPPORTED` |

MISSING   main.o → config.h

### 检测依据

**MD 的证据链**

| 环节 | 证据 |
|---|---|
| 实际读取 | `work/e6-before-02/evidence/trace/t.15` 第 579 行：`openat(AT_FDCWD, "config.h", O_RDONLY\|O_NOCTTY) = 4` |
| 进程归属 | `processes.json`：PID 15（`cc1`）的父进程是 14（`cc`），14 是 make（PID 13）的直接子进程 → job 14 |
| 输出目标 | `work/e6-before-02/evidence/trace/t.16` 第 23 行：`openat(AT_FDCWD, "main.o", O_RDWR\|O_CREAT\|O_TRUNC, 0666) = 3`（as 进程写 main.o） |
| 声明缺失 | `make-db.txt` 第 1053 行只写 `main.o: main.c unused.h`，不含 `config.h` |

**RD 的证据链**

`make-db.txt` 第 1053 行声明了 `unused.h`，但整个 trace 中没有任何进程成功读取它。

### 进程归属（对应自主任务第 1 问）

`processes.json` 的实际内容：

| PID | 父进程 | 所属 job | 可执行文件 |
|---:|---:|---:|---|
| 13 | — | —（make 本身） | `/usr/bin/make` |
| 14 | 13 | 14 | `/usr/bin/cc` |
| 15 | 14 | 14 | `cc1` |
| 16 | 14 | 14 | `/usr/bin/as` |
| 17 | 13 | 17 | `/usr/bin/cc` |
| 18 | 17 | 17 | `collect2` |
| 19 | 18 | 17 | `/usr/bin/ld` |

**处理方式**：`fullcheck.py:131` 的 `job_for()` 从进程沿父链向上爬，**遇到 make 的直接子进程就停止**，该子进程即 job 根。因此 14/15/16 属于同一个 job（编译 `main.o`），17/18/19 属于另一个 job（链接 `app`）。每个 job 内**最后写出的文件**就是该 job 的目标。PID 每次运行都不同，上表是本次运行的实际值。

### 路径过滤（对应自主任务第 1 问）

`fullcheck.py:60` 的 `project_path()` 先把路径规范化为绝对路径，再判断是否位于项目根目录之下；不在根目录下的返回 `None`，后续直接跳过。

因此 `/usr/include/stdio.h`、`/tmp/cc*.s` 以及 `/course/project-other/` 这类同前缀但不同目录的路径都不会成为依赖。代码还额外跳过 `O_DIRECTORY` 和 `O_PATH` 的打开。

## 故障与限制

### 1. 环境故障（非目标故障，均记录处理过程）

| 故障 | 现象 | 处理 |
|---|---|---|
| **Docker Hub 不可达** | 构建时解析 `docker.io` 元数据耗时 60s + 120s 后超时 | 从 `docker.m.daocloud.io` 拉取，digest 与课程指定值**完全一致**（`sha256:f82c964...`），再打本地 tag |
| **Debian apt 源过慢** | 首次构建 14 分 33 秒仍未完成 `apt-get update`，被手动终止 | Dockerfile 中把 `deb.debian.org` 换成阿里云公网源 `mirrors.aliyun.com`，并加入失败自动回退 `deb.debian.org` 的逻辑；第二次构建约 2 分钟完成 |
| **PyPI 直连慢** | 构建中 `pip install` 阶段耗时约 110 秒 | 未改镜像源，接受该耗时；依赖按 `requirements-dev.lock` 哈希校验安装，内容不受影响 |
| **BuildKit 前端镜像** | `# syntax=docker/dockerfile:1` 触发额外 60 秒解析 | 删除该注释行；本 Dockerfile 未使用任何 BuildKit 专属语法，镜像内容不变 |
| **内存低于要求** | `doctor` 报告 `mem_gib=3.5`，低于最低要求 4 GiB | 在 3.5 GiB 下实测构建、E5、E6、8 项门禁均通过；尚未在更高内存环境复测 |
| **CPU 低于建议值** | 2 vCPU（建议 4） | 同上，未复测 |

上述 Dockerfile 修改只影响**下载路径**，不改变镜像内工具版本；`/opt/toolchain.lock` 记录的 gcc 14.2.0、make 4.4.1、strace 6.13 与课程指定版本一致。

### 2. 目标故障（E7 场景，属于预期行为）

见 E7 门禁表第 6–8 项：`build-failed`、`unsupported`、`timeout`。这些场景返回退出码 1 表示**程序正确识别了故障**，不是失败。
